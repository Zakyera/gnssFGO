STEP COMPLETE: remaining cost localized; acceleration not yet implemented.

1. Outcome and scope

The remaining LOCAL update is a genuine serial part of GLIM's scan-processing
critical path, still using generic GTSAM iSAM2. E1 batches LOCAL covariance
reconstruction only; it does not batch this update. Native GLIM's main smoother
already uses gtsam_points' GPU-aware iSAM2 extension.

Important qualification from the completed live160 capture: the MAIN smoother
now consumes more measured time than LOCAL. In the last40s, main=55.37% and
LOCAL=33.44% of matched scan wall time. LOCAL acceleration is justified, but it
cannot alone remove all source delay. Neither component is measured as pure
CPU or GPU time: contention, synchronization and other-process work can affect
wall timers. No speedup or fix is claimed by this diagnosis.

The LOCAL active state count is bounded, not an ever-growing trajectory:
150/153 keys before marginalization after startup (pose/velocity/bias for about
50 scans); GLIM reports49/50 active frames after retirement. Every retained LOCAL
lifecycle row reports zero external CBS factors. We must not explain its cost
as retaining the full source trajectory or repeatedly marginalizing Kimera
factors there. The receiver's full-history growth is a separate issue.

No estimator run, new trajectory, tuning, solver/library upgrade or estimator
source edit was performed. This is the single E1b.1 step in the saved plan.

6. Next single step: E1b.2, measurement-only LOCAL subphase profile

Do NOT swap to a GPU batch optimizer or rewrite fixed-lag iSAM2 yet. Implement
one opt-in, default-OFF instrumentation patch in an isolated candidate build:

- Scoped thread-local context identifies MAIN, LOCAL_UPDATE, LOCAL_COVARIANCE,
  revision export and OTHER. Do not confuse concurrent native/global processes.
- Measure existing work only: input bookkeeping, BPSAM backup/copy, BaseSAM
  update, post-estimate/guards, marginalizeLeaves, cleanup.
- Within existing calls aggregate synchronous GPU linearization/error count
  and duration; separate nested error->linearize time to avoid double-counting.
  Reuse existing GTSAM timing sites where practical to partition factor work,
  elimination/reordering and back-substitution, without adding evaluations.
- Record already-available ISAM2Result relinearized/re-eliminated counts,
  active keys, non-null/allocated factor slots, retiring keys and factor types.
  Do not call calculateEstimate(), error(), linearize() or marginals just to
  measure them. No additional GPU synchronization for timing. Host elapsed
  times are not GPU kernel timings; record that distinction.
- One aggregate row per scan/update, no per-factor log storm; include unassigned
  wall time and validate nested/disjoint accounting and exception-safe scope.

Before any performance capture: test instrumentation OFF equivalence, scope
nesting/exception restoration, zero extra solver/factor evaluations, cache
consumption unchanged and shared-factor ownership. Exercise the existing E1
GPU fixtures (including sync-preserving cache/inlier behavior), Release and
focused sanitizer tests. Keep production binaries intact and record hashes.

Then request a separately bounded profiling capture using the frozen source
profile; no ATE sweep or automatic full160 rerun. A short capture can identify
per-update cost but must not be labeled a reproduction of the120-160s tail.
Profiling can perturb live availability, so exact live event equality is not
an honest requirement; require deterministic same-input fixture equality and
unchanged call/evaluation counts, then disclose measured logging overhead.

Decision from those measurements: choose ONE measured dominant subphase for
an equivalent acceleration patch. The leading candidate remains reusing the
existing gtsam_points batching for the actual affected LOCAL factor set at the
exact iSAM2 Values, preserving E1's synchronous semantics. Backup/post-estimate
work is a secondary candidate only if measured material. No global BPSAM base
replacement, no extra full-graph prelinearization each update, no shortened lag,
no dropped revisions and no weakened rollback/publication checks.

Stop rule: do not repeat an uninstrumented long run or start multiple speculative
optimizations. If a profile cannot attribute the time, fix its instrumentation
first rather than claim that a solver upgrade will solve it.
