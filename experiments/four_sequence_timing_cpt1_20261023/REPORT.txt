CP-T1 — FOUR-SEQUENCE OPTIMIZATION AND THROUGHPUT AUDIT
Completed 2026-10-23. Saved telemetry only; no new experiment.

BOTTOM LINE

0.5x is a credible next throughput test, not an operating point certified by
these 0.20x recordings. GLIM is the limiting pipeline. Kimera and the bounded
WNOA receiver have substantially more measured headroom. The current dominant
sustained source cost is calculating/exporting beliefs and their covariance
revisions, not the MAIN nonlinear solve alone. The largest CBS-ON injection
spikes are associated with the capped passive covariance-competition audit.

MAIN GPU batching is still effective: every recorded MAIN profile has zero
synchronous GPU-linearize calls. There are no separately optimized LOCAL
profile sessions. This is not evidence that all GPU evaluation throughout the
process is absent: the passive audit itself performs extra factor evaluation
and local marginal calculations outside the MAIN profiling context.

No settings, covariances, revisions, diagnostics, binaries, playback rates or
captured results were changed. No containers or estimators were launched.

therefore repeat costly GPU-backed work outside MAIN batching. It is capped
at40samples withstride20; its growing early cost is not unbounded source state.

Consequences:
- All measured sustained20s windows have capacity in the unchanged-service
  projection. This supports TRYING0.5x rather than assuming0.1x is necessary.
- Bursts matter: ETH1 OFF reaches102.2% in a5s physical window; LEICA-2 ON
  reaches95.4%, and short1s windows reach166%. A queue can briefly grow even
  though it later drains. P95 alone is not a hard real-time guarantee.
- In a simple fixed-service FIFO illustration, GLIM reaches about1.33s maximum
  wall waiting in ETH1 OFF and1.17s in LEICA-2 ON at0.5x. This uses scan-ready
  timestamps and recorded service costs; it is NOT a receiver/estimator replay,
  arrival-chain model or retention-window acceptance certificate.
- Raising the replay rate increases simultaneous CPU/GPU/memory/I/O demand.
  Saved0.20x service times may increase. There is no complete hardware-utilization
  trace here to rule that out. Clock-to-source delays and CBS availability in
  physical time also change, potentially changing numerical trajectories.

Observed0.20x health: GLIM remaining internal queue maximum1 in every case;
receiver monitored queue maxima8--23, transport maximum37--49. Receiver
receipt-to-processing p95 across cases18.2--31.5ms; worst whole-run maximum
587ms in ETH1 OFF, versus35--103ms in the other7cases. This excludes upstream
sensor-to-belief creation latency and does not validate0.5x.

6. RECOMMENDATION / STOP

Recommend one explicitly authorized headless0.5x throughput test before calling
it the official rate; no model/covariance/lag changes are indicated by this
analysis. It should include a previously busy portion, not only quiet startup,
retain valid quiet initialization, and keep existing conservation, expiry,
coverage, delay and growing-queue checks. Do not relax guards to claim success.

The first engineering target, IF needed, is the passive heavy competition
audit, which should be isolated from the time-critical incoming-factor path or
disabled only in a clearly declared throughput profile. Preserve the archived
audit evidence. Removing it is not performed here; timing/cache effects and
causal ordering still need a bounded comparison, not an assumption of bitwise
identity. It must not silently disable required covariance/revision logging.

The next sustained-cost target would be covariance/revision computation and
export in GLIM/Kimera, and per-version transactions in fusion. Reuse verified
work before considering changed publication cadence. Do not silently drop
revisions, change uncertainty, extend lag or retune WNOA to improve timings.

Decision:0.5x is plausible, with GLIM as the first bottleneck. Not yet validated.
No higher-rate experiment or implementation change started. Stop at this audit.
