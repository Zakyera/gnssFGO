1. WHAT THE FRAMES ACTUALLY MEAN
==============================
Notation: T_A_B maps a point expressed in B into coordinates expressed in A.
B = cpt7_imu; C = camera; L = LiDAR; Wg/Wk = independent estimator world frames.

Stage                  GLIM                         Kimera
Input observation      Hesai/Velodyne points        Alphasense stereo pixels
Inertial input         /boxi/cpt7/imu               /boxi/cpt7/imu
Graph pose X_i         T_Wg_B(i)                    T_Wk_B(i)
Visual/geometric       LiDAR points transformed     Camera pose = X_i*T_B_Crect
factor frame handling  by T_B_L before matching     (rectified left camera)
CBS mean               inv(X_i)*X_j                 inv(X_i)*X_j
Mean's body convention B_i <- B_j                  B_i <- B_j
Message world label    map                         odom
Configured body        cpt7_imu                    cpt7_imu
Boundary body change   identity                    identity

The header strings map and odom are different world labels. They do not mean
that the relative motion has to be rotated from one global map into the other.
For any constant world transform G:
    inv(G*X_i)*(G*X_j) = inv(X_i)*X_j.
That cancellation is why relative body motions can be exchanged without first
globally aligning the two independent maps. It does NOT permit changing which
physical body or sensor is represented by X.

For different physical body frames, E=T_B_S would instead require:
    Delta_S = inv(E)*Delta_B*E
    Delta_B = E*Delta_S*inv(E).
This includes the lever arm; rotating only the translation vector is not enough.
Kimera's ROS wrapper has this conjugation in its nonidentity configuration.
Here external_pose_frame_id == base_link_frame_id == cpt7_imu, so it is skipped.
GLIM expects the configured external body convention directly. Kimera publishes
in that configured external convention when they differ; there is not a second
GLIM-side camera conversion to apply.

Important contract limitation: a CBS message carries a world header label but
does not itself provide a separately enforced body-frame identity. Correctness
therefore depends on the matched configuration. This is a future hardening
opportunity, not an observed mismatch in these runs. No hardening patch applied.

3. SENSOR FRAME -> NATIVE GRAPH -> EXPORTED BELIEF
================================================
GLIM's profiled odometry source reads T_lidar_imu, takes its inverse, transforms
initial/deskewed points into IMU coordinates, and optimizes X=T_world_imu. The
LiDAR pose is separately formed as T_world_imu*T_imu_lidar. The CBS bridge queries
the optimized X endpoints directly and exports from_pose.between(to_pose).
It does not export the separately derived LiDAR pose or global-map optimized pose.

Kimera parses T_BS as body_Pose_cam. Stereo rectification produces
T_B_Crect=T_B_Craw*[R_rectification^-1,0]. The same rectified-left transform is
used by the native smart stereo factors and stereo-motion body conjugation.
The backend's CBS exporter queries native graph endpoints; it is NOT taking
differences of the independently accumulated incremental ROS trajectory.
Method1/Method2 plotting/scoring choices therefore do not change this CBS mean.
An exported relative mean can use the CURRENT revised endpoint states; that is
different from mixing two previously published absolute states from two solves.

The mean wire format is SE(3) Logmap with rotation first, translation tangent
second. The translation tangent is not generally the pose's xyz displacement.
Both receiver paths reconstruct with SE(3) Expmap, not an xyz shortcut. The audit
compared full 4x4 transforms, including quaternion order and translation.

Native saved visual-factor check (saved_native_attempt3/results.json):
  CP51 OFF update6:291 smart factors, body-transform/calibration discrepancy0.
  CP51 ON update6: 291 smart factors, body-transform/calibration discrepancy0.
  Native stereo baseline .110084692571745m.
The reader used the retained Kimera library and saved native graph; no graph
linearization or optimization. Before/after serialized graph bytes are identical.
This verifies the active optical/rectification convention, not merely YAML labels.

6. SECONDARY FINDINGS — NOT THE CBS-ON CAUSE
=========================================
A) Right-camera visualization metadata defect:
StereoCamera.cpp:65 forms B_Pose_camRrect_ using LEFT camera body pose rather
than RIGHT. Native readback confirms the right-camera metadata has the same
origin as the left, despite the actual .110085m stereo baseline, and their
reported rectified orientations differ1.19224degrees instead of being parallel.
The backend uses LEFT rectified pose plus the CORRECT stereo calibration, as
the291factor checks prove. The right-pose getter feeds visualization/playground
metadata, not the active stereo factor or CBS export/insertion path. The checked
runs are headless. This cannot be used as an explanation for the poisoned
Kimera CBS mean or the body trajectories in the current Rerun exports. No fix
applied under this diagnostic task; keep it separate from the CBS investigation.

B) Saved GLIM process maps include OpenCV3 and4; Kimera maps use OpenCV4 core.
This is dependency-hygiene evidence, not a demonstrated frame or estimator bug.
The checked CBS means use Eigen/GTSAM and match native endpoints. A standalone
camera reader initially mixed OpenCV versions due to an inherited test build
recipe; it was repaired in a fresh attempt using the actual camera compile
recipe and OpenCV4 link. Do not conflate that new test-executable fault with a
failure in the original campaign. All failed attempts remain saved.

7. LIMITS AND RECOMMENDED DECISION
================================
We have strong evidence against wrong-camera-versus-LiDAR body interpretation,
inverse/static calibration mismatch, missing lever arm, double spatial transform,
map-versus-odom conversion, quaternion ordering or Expmap translation corruption
in the tested EIG-2 paths. The causal G2K first-admission factor is covered by
native evidence. It is not justified to change the extrinsics or add a transform.

What remains unproved:
  - physical accuracy/rigidity of the manufacturer's calibration itself;
  - native GLIM final inserted-factor matrices, absent from historical observer;
  - every possible asynchronous/order/linearization issue outside captured checks;
  - complete historical source-to-binary equivalence for every explanatory file.
source_audit.json distinguishes7historically pinned explanatory sources from
8current-source explanations. Runtime payloads, library maps, saved visual
factor data and native numerical tests supply separate evidence; none replaces
the missing provenance with an assumption.

Do not resume blind frame fixes or covariance tuning from this result. The next
frame-specific experiment, ONLY if closing the last K2G observation gap is
needed, is a short passive GLIM factor-measurement capture with unchanged settings,
not another full mission. No such capture was launched here. Otherwise this
audit supports returning to why a correctly expressed conflicting relative
motion drives the coupled native window response; it does not yet establish
that covariance weighting alone is the cause.
