CP-V34 — EIG-2 VELODYNE / KIMERA METHOD 1 SHAKING
Saved-data diagnosis, 2026-10-29
================================================

VERDICT
The spikes are present in the saved MAIN graph estimates, not introduced by
Rerun. Their dominant CBS-ON mechanism is coherent repositioning/rotation of
Kimera's active window between optimizer updates. This is quite different from
the robot moving backwards/forwards, or the local stereo trajectory repeatedly
expanding and shrinking. CBS-ON amplifies the absolute-window corrections.

No evidence was found for different physical IMUs accidentally treated as one,
or a camera/LiDAR-frame transform accidentally applied on the GLIM-to-Kimera
transport examined here. Those checks do NOT prove that all calibration,
preintegration, covariance, marginalization or optimizer code is correct.

The exact initiating defect is NOT yet identified. Prior/global anchoring and
incremental linearization under competing, very tight peer factors is the
strongest next investigation. Temporal mean alignment with unchanged covariance
is a second concrete modeling limitation to isolate. Baseline OFF deformation
also warrants native VIO/initialization checks. Do not label this a proven
CP-K9 bug, a proven bad Velodyne calibration, or harmless plotting alone.

No estimator/receiver run, build, container operation, parameter change, repair,
default promotion, deletion or push was performed. This is original CP-V4,
receiver Qc multiplier 1.0, not the later 0.25 ablation. WNOA is downstream and
does not generate the GLIM beliefs arriving in Kimera.

3. THE LARGE SPIKES ARE MOSTLY WHOLE-WINDOW CORRECTIONS
------------------------------------------------------
At update k, with p(i|k) the pose i after update k:

  Method 1 displacement = p(k|k) - p(k-1|k-1)
                        = [p(k-1|k) - p(k-1|k-1)] + [p(k|k) - p(k-1|k)]
                          previous-pose revision       same-update motion

This is an exact VECTOR identity. Norms of the two terms do not generally add.
The old historical Method 1 output is not replaced when the window is revised.

4. USER HYPOTHESIS 1 — DIFFERENT IMUs TREATED AS THE SAME
--------------------------------------------------------
Not supported by saved execution evidence:
  * Actual Kimera argv remaps imu:=/boxi/cpt7/imu.
  * Saved GLIM config uses /boxi/cpt7/imu, cpt7_imu body/IMU frame, acc_scale1,
    imu_time_offset0 and points_time_offset0.
  * Actual source metadata selects alphasense_front_stereo+cpt7_imu for Kimera
    and velodyne+cpt7_imu for GLIM. Kimera T_BS is identity; rate100Hz,
    imu_time_shift0, automatic IMU/camera time alignment disabled.
  * Original bag preflight records35502 CPT7 messages, max gap10.001ms.
  * Both actual body frames and Kimera external-pose-frame setting are cpt7_imu.

Do not infer a different IMU from unused launch defaults, or from the historical
directory name eth1_mono_shared_cpt7. Actual execution here is stereo/shared
CPT7. Kimera's +Z gravity convention and GLIM's world orientation need not be
equal world frames; this does not by itself mean different body axes/IMUs.

Limits: same physical source does not imply identical preintegration/noise
models, and no hash of every per-consumer IMU callback packet was retained.
Wrong integration conventions or dropped/interpolated support inside a consumer
would require the focused packet-level replay below, not a claim based on names.

5. USER HYPOTHESIS 2 — WRONG BODY FRAME / BELIEF TRANSFORM
---------------------------------------------------------
No transport-frame error was found in the examined route:
  * Original calibration preflight compared frozen profiles to raw TF paths:
    left/right camera max difference1.94e-12; Velodyne2.29e-13;
    prism7.66e-10. These establish consistency with dataset calibration, not
    independent physical calibration accuracy.
  * GLIM's private exporter uses MAIN from_pose.between(to_pose), where the
    LIO graph pose is the IMU/body pose. The Velodyne extrinsic is already in
    the LIO measurement model; it must not be applied again to that belief.
  * All3540 incoming GLIM beliefs exactly match saved GLIM endpoint exports.
    Recomputing endpoint relative transforms gives max translation difference
    1.87e-14m and rotation5.20e-13deg.
  * For all1744 Velodyne aligned candidates, incoming bag mean vs Kimera raw
    mean differs by at most2.22e-16 per component, covariance exactly equal.
    Same check passes all1740 Hesai candidates. No unexpected conjugation,
    inversion or order swap occurs between these saved stages.
  * Kimera base and external body frame are both cpt7_imu; wrapper code's
    optional body-frame conversion branch is therefore not needed.
  * Aligned mean and covariance exactly match the subsequent frozen candidate
    record. Candidate count is not an assertion that every candidate merged:
    observed merge-row counts are1699 Velodyne and1721 Hesai.

The GLIM message header says map and Kimera output says odom. These world-frame
names do NOT require rotating a body-relative belief by a guessed map-to-odom
transform: (G*X_i)^-1*(G*X_j) = X_i^-1*X_j. Different sensor BODY frames would
require an extrinsic conjugation; this checked route uses the same body frame.

This validates the saved exporter/transport arithmetic, not every deskew,
reprojection or covariance tangent/Jacobian computation in the estimators.

6. TIMING / COVARIANCE IS A REAL REMAINING SUSPECT
------------------------------------------------
For matched GLIM-to-Kimera candidates (sender time minus receiver time):

                                  Velodyne median / max     Hesai median / max
Endpoint displacement in time      ~41.18 / 49.47 ms          ~17.34 / 18.83 ms
Mean translation correction         5.879 / 32.113 mm          2.418 / 13.890 mm
Mean rotation correction             .394 / 3.541 deg          .180 / 1.394 deg

These are different sensor endpoint times, not proof of a clock error. Sender
intervals are about200ms, matching receiver intervals about200ms. Saved source
and logged source timestamps match exactly after the same double-to-ns rounding.
All examined alignments obey the logged causal availability bound. Velodyne's
existing sensor-time audit passes and all published scan intervals have IMU
bounds; that old audit explicitly is not a full independent deskew-equation audit.
Some interleaved GLIM pairs miss the50ms endpoint gate and are rejected/retried;
they must not be silently treated as accepted or used to relax the guard.

The code uses native-IMU temporal bridges on both ends of the relative factor.
But the covariance is copied unchanged. Bridge uncertainty/correlations and
the full covariance transformation are not represented. This is the previously
declared mean-only approximation, not a newly discovered hidden frame swap.

Across Velodyne candidates, marginal rotation sigmas have axis medians
(.003673,.002856,.005637)deg; translation sigmas(2.009,1.522,1.046)mm.
Hesai corresponding medians(.003506,.002712,.002814)deg and
(1.083,.896,1.005)mm. These are local-coordinate marginal standard deviations,
not calibrated total state uncertainty or independent likelihoods.

At the6.34m revision event, the incoming aligned relative motion is only
0.117894m; before update it differs from Kimera's same-edge relative estimate
by31.86mm and0.2947deg. Temporal alignment changes the GLIM mean by6.23mm and
0.3383deg. The rotational marginal sigmas are about.00194--.00356deg.
After update the edge disagreement is22.57mm and0.1786deg, while the window
moves meters. The incoming message does NOT directly command a6m step.

These large disagreements compared with small reported marginal sigmas make
uncertainty/linearization compatibility a priority. They are NOT a valid NIS
test: receiver uncertainty and shared-IMU/cross-factor correlations are omitted.
The magnitude of a legitimate mean correction is also not its estimation error.
Do not claim timing caused the spikes solely from these comparisons.

7. WHY PRIOR / SOLVER DIAGNOSIS COMES NEXT
-----------------------------------------
The graph has strong initial priors: initial position sigma1e-5m, yaw0.1deg,
roll/pitch10deg, velocity.001m/s;25keyframe horizon, numOptimize1,
relinearizeThreshold.01, relinearizeSkip1, wildfire.001, no Dogleg.
Therefore 'just no/weak initial prior' is not established. What matters is the
effective marginalized prior, fixed-variable bookkeeping and nonlinear
linearization later in the mission, not only an initial YAML number.

The executed private Kimera DSO is CP-K9, SHA256
be637ad745f73bf12596d3bf06754f56ed7bcadfdb8b4792b94c4fcfee62aad9.
Selectors: CPK9_PRIOR_REFRESH1, FL4Q_ENABLE0, FL4M_RETIREMENTremove.
CP-K9 releases accounted native fixed-key locks at actual temporary-peer
retirement after wrapping the original marginal prior in its immutable chart.
Its historical focused tests passed; those are not proof of nonlinear
stationarity or real-sequence conditioning at these large updates.
OFF has no peer retirement activation and still shakes, so CP-K9 alone cannot
explain the entire baseline symptom. ON adds both peer constraints and their
retirement/refresh path; these effects must be separated.

A correct relative pose factor is invariant under a common world transform.
It does not directly tell Kimera where its whole window should sit in the
world. Through interaction with IMU/visual/prior terms and linearization it can
nevertheless change the global solution. The observed nearly rigid, yaw-heavy
motion makes that interaction a stronger lead than wholesale scale collapse.
This does not prove a free gauge/nullspace: the retained prior can constrain it.

There is also a startup qualification: the original retained Hesai-matched
window did NOT pass the later strict quiet-start check (gyro norm p95.01782rad/s,
image difference2.5349). Possible initialization/bias effects remain open;
do not change the startup crop in the first reproducer and confound the test.

8. PROPOSED MINIMAL DISCRIMINATING EXPERIMENT — NOT LAUNCHED
-----------------------------------------------------------
First reproduce Kimera only, unchanged camera/CPT7/profile and original start,
OFF then ON with the SAVED Velodyne incoming belief stream. No new GLIM run or
fusion campaign is needed. Use original pacing and preserve receipt/order;
require matching keyframe IDs, factor admission/retirement and pose histories
before drawing conclusions from a replay. A cropped cold start near a spike
would not reproduce the accumulated marginal prior.

Bound to300sensor-seconds from the original start: this covers the large ON
events around201--220s and the OFF peak near267.8s. Instrument only targeted
updates to control overhead; retain failed evidence if parity fails.

At each target update save full states/velocities/biases and factor graph at:
  A. entry / native new-measurement preparation;
  B. peer insertion and the solve;
  C. temporary factor retirement, prior promotion and relinearization;
  D. marginalization / final published state.
Place hooks at the actual implementation stages; do not infer intermediate
states from final output or conflate sequential phases when code combines them.

Record prior anchors/Hessian/gradient, fixed keys and cache identities; factor
costs split into visual, IMU, marginal prior and peer; update delta, nonlinear
gradient and step acceptance; exact IMU packets and both temporal bridges.
Evaluate costs on consistent snapshots and graphs. Before/after graph changes
need not have the same objective, so a raw total-cost difference is not enough.

Then use captured snapshots for read-only diagnostic clones, one question at
a time, without modifying or promoting the baseline:
  * Same objective, fully refreshed and converged reference solve: if the
    original update moves meters but this stable solution does not, investigate
    incremental cache/linearization/convergence rather than tune a weight.
  * Prior/retirement equivalence and gauge-direction checks: if the function or
    information changes incorrectly at removal/promotion, repair that identity.
  * Independently reconstruct timestamp/body-frame bridges from saved packets;
    examine properly transported uncertainty including bridge uncertainty and
    shared-input correlations. Do not simply disable alignment or inflate a
    covariance until the line looks smooth.
  * If native OFF already changes local shape, inspect initialization/bias and
    stereo smart-factor residuals/conditioning using the same frozen inputs.

Success is an explained, repeatable mechanism with a targeted regression test,
not just a lower ATE or smoother display. Only after diagnosis should one
isolated fix be evaluated with BOTH absolute and incremental evo ATE/RPE,
path length, coverage and retained prior/lifecycle checks.
