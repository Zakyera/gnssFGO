2. Actual corrupting write, not just the allocator assertion
glim_ros1/src/glim_ros/glim_ros.cpp:109 allocates:
  cbs_bridge.reset(new glim::GlimCbsBridge(nh));
The allocation size is compiled into glim_ros.cpp.o, not dynamically obtained
from the constructor library. E1b.2 build.py rebuilt the instrumented bridge
but reused the older workspace allocator and inspector objects from link.txt.

Disassembly excerpts, hashes and exact paths are in validation.json under

flags as the private compile, not a guess from timestamps or source text.

ASan negative control retains the stale allocator and instruments the current
bridge constructor. The actual no-data GLIM process reports:
  ERROR: AddressSanitizer: heap-buffer-overflow
  WRITE of size 8
  GlimCbsBridge::GlimCbsBridge(ros::NodeHandle&)
  .../overlay/cbs_bridge.cpp:646
  0 bytes to the right of 3296-byte region
  allocated by operator new -> GlimROS::GlimROS

Line646 is the constructor/member-initialization location. The report does
not identify one particular member by name; it does prove a write outside
the allocation while constructing the larger object. The 48-byte shortfall
explains why malloc detected corrupted heap state later in the failed run.
Evidence: evidence/asan_bad/node.log. No sensor processing was needed.

This does not implicate the working E1/E2 libraries: E1's allocator already
uses3344, and those binaries/results retain their original hashes. The defect
was introduced by the private profiling build recipe's stale-object reuse.

and CUDA are not fully instrumented; actual-node leak checks are disabled.

warnings. Release checks do not. These tests validate the constructor write
repair, NOT GPU workload correctness under ASan or actual CUDA capacity.

is not claimed to have fixed that intermittent failure. No system ASLR/ptrace
