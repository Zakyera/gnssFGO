E2 — exact same-input receiver linearization reuse
=================================================

Decision
--------
CORRECTNESS_PASSED_PERFORMANCE_NOT_CERTIFIED. E2 is complete as a bounded
experiment. Keep the candidate default-off and do not replace the working
receiver. Exact reuse is numerically valid on the tested journals and saves
derivative calls, but timing variability prevents a reliable adopted speedup.
It does not solve growing full-history work or certify live queue headroom.

What was investigated
---------------------
The actual normal path in FullPublicationRefinement.h evaluates graph error and
NormalizedGradient at the current Values, forces full relinearization/solve, and
evaluates the resulting Values again. An earlier Gaussian evaluation cache is
used in recovery/stable-cost handling, not as a general normal-path cache.
The retained live60 has 649 accepted ordinary refinement steps and no recovery
or stable-cost steps. The retained partial143 has 2209 step rows, including 18
recovery rows and two local-prediction rows; 51 rows have nonzero stable-cost
diagnostics. Optimizing only that rare branch would miss the ordinary workload.

The observing-only wrapper executes EVERY original factor linearization. It
compares each call with the immediately preceding successful call to that SAME
factor object using bit-identical referenced Values, not a numerical tolerance.
Keys, stored pose rotation matrix/translation, V/W and active flag are included.
The pinned GTSAM uses matrix rotation storage, not GTSAM_USE_QUATERNIONS.

Candidate and its limits
------------------------
ExactLinearizationMemo.h wraps the existing WNOA/relative factor classes. It
does not replace any error function, derivative, whitening or solver policy.
E2_EXACT_LINEARIZATION_CACHE=1 is required; default is off. The implementation
keeps only the last successful finite Gaussian linearization per factor object.

- Every referenced state bit must match. One-bit V/W/translation changes and
  tiny pose rotations miss; unrelated Values may change without invalidating.
- New factor versions and clones start empty. The receiver constructs a new
  immutable factor object for replacement, so mean/noise/endpoint revisions do
  not share cache entries. This is NOT a generic in-place mutable-factor cache.
- A cache hit returns a CLONE, never the stored Gaussian object; a caller cannot
  poison the cache by mutating its returned matrix.
- A miss clears the old entry before calling the unchanged implementation.
  Exceptions clear the entry and rethrow. Inactive factors bypass caching.
- A per-factor mutex prevents concurrent different-Values calls returning a
  mismatched entry. Diagnostic counters are atomic.
- Full current-Values gradient checks, forced relinearization, transactional
  rejection and all publication criteria remain unchanged.

Costs are real: signatures/locking/accounting on all calls, Gaussian cloning on
hits AND successful misses, plus finite checks/materialization of a weighted
augmented Jacobian on misses. GTSAM's augmentedJacobian() returns a dense weighted
matrix by value. The candidate calls it for validation and byte accounting.
This code inspection identifies extra work; no per-operation time attribution
was measured, so it does not prove which individual overhead dominates.
The cache still visits the full graph; it does not fix history-size growth.

The short repeat is numerically identical to the first pair and the old retained
replay, including identical cache-hit counts. The first candidate took almost
1.87x its repeated time with the SAME binary/data. Do not discard that first
sample, average these different workloads into a headline speedup, or claim the
first slowdown proves caching intrinsically fails. Conversely, the single 25%
longer-journal improvement is not a certified universal gain. CPU user+system
times track wall times (saved60 candidate 105.441 vs repeated 56.408 s); this is
not just waiting in the controller. Scheduling/core placement/frequency/shared
machine effects were not controlled or logged sufficiently to identify the
cause. No other owned heavy experiment was launched concurrently; a container
process snapshot showed the reference alone using ~100% of one CPU.

The reverse-order pair suggests a modest possible benefit (~5.1% total time),
not elimination of the bottleneck. In that pair late publication p95 slightly
WORSENS (131.594 -> 132.954 ms), despite a lower median. The observed larger
long-journal hit rate is real and deterministic; its precise speed benefit is
not isolated by this small uncontrolled timing sample. No extra timing retries
or post-result cache edits were made.

Recovery and next-task boundary
-------------------------------
The candidate remains isolated/default-off and the original executable remains
available at the path/hash above. No existing receiver executable, launch or
profile is replaced. Do not automatically proceed to E1b, E3, E4 or a live run.
Any further engineering hypothesis requires a separate decision and validation.
The ordered plan's next unstarted mathematical-kernel task is E3a (remaining
WNOA derivatives). It attacks calculations that must still be performed rather
than relying on exact repeats. It needs its own derivative/reference gates; it
is NOT authorized or implemented by this E2 report. A performance adoption of
E2 would instead need a separately agreed controlled timing check. Neither is
silently launched here.
