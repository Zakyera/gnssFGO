## Belief extraction check

The logged source sequence is [VioBackend::optimize](/home/yeranis/repos/V4RL/cbs_gtsam4.3/src/Kimera-VIO/src/backend/VioBackend.cpp:4486) `updateStates`, then `refreshCbsOutgoingBeliefs`; no optimizer step intervenes. In [the revision logger](/home/yeranis/repos/V4RL/cbs_gtsam4.3/src/Kimera-VIO/src/backend/VioBackend.cpp:3070), revision zero is the actually published first belief; later revisions request precisely `{x_i,x_j}` from `smoother_->getOdometryBeliefs`, then read `calculateEstimate<Pose3>` for those same two keys. [BPSAM::getOdometryBeliefs](/home/yeranis/repos/V4RL/cbs_gtsam4.3/src/cbs/src/bpsam/bpsam.cpp:2548) computes `from_pose.between(to_pose)` and the relative covariance using the joint marginal information from that smoother. The export uses `Pose3::Logmap` with GTSAM `[phi,rho]` order, radians and metres; it does not use a nearest-time pose lookup.

For all 175 selected revision records I independently reconstructed `\hat Z=X_i^{-1}X_j` from the two poses **in the same source log row**, then evaluated `Log(Z_logged^{-1}\hat Z)`. Maximum rotation norm was `9.24e-15 rad`; maximum translation tangent norm was `1.48e-13 m`. Exact pair indices, consecutive ordering, revision number, backend update (`u=j+r`), first/active status, and both physical endpoint timestamps matched the exported rows; no selected edge reused a source index under another ID. All 36 exported covariance elements equal the corresponding source-log elements exactly; maximum asymmetry was zero and the smallest selected 6×6 eigenvalue was `2.83e-9`. Thus the **mean extraction is independently verified** and the covariance export is byte/numerically the logged source result. An independent recomputation of the covariance from the joint marginal Hessian is **not possible** because that Hessian was not retained. The code establishes that the logged covariance was requested from the same smoother snapshot; that is not an independent numerical proof of its underlying marginal calculation.

## What changed at the bad updates—and what was not retained

The 25 consecutive logged outgoing edges at update 1084 span pose IDs 1059–1084; at update 1093 they span 1068–1093. These are the *observed belief-query pose keys*, not an independently verified inventory of all graph variables or factors. The saved [configuration](/home/yeranis/repos/V4RL/cbs_gtsam4.3/runs/_eig2_kimera_full_revision_20260924/full305/grandtour_launch_used.launch:261) set active CBS-factor diagnostics off; the [factor-graph audit flag](/home/yeranis/repos/V4RL/cbs_gtsam4.3/src/Kimera-VIO/src/backend/VioBackend.cpp:150) defaults off; [Rerun factor-graph output](/home/yeranis/repos/V4RL/cbs_gtsam4.3/runs/_eig2_kimera_full_revision_20260924/full305/resolved_kimera_params.yaml:27) was off. The 483 MB `estimators.log` contains revision/timing rows but no `KIMERA_FACTOR_GRAPH_AUDIT_ROW`, `KIMERA_FACTOR_GRAPH_FACTOR_DETAIL_ROW`, or exact marginal-prior rows. There is no retained Kimera graph/checkpoint in `full305`; its `glim_dump/graph.bin` belongs to GLIM, not Kimera. The recorded CBS bag contains published beliefs and odometry, not Kimera's private optimizer graph. The timing-row `cbs_marginalization_graph_factor_count` is the **local CBS covariance graph** count; it must not be mistaken for the active optimizer's factor count or the number of marginal priors.

Static code shows the *possible* factor families: the selected IMU configuration (`imu_preintegration_type:1`) uses `CombinedImuFactor` in [addImuFactor](/home/yeranis/repos/V4RL/cbs_gtsam4.3/src/Kimera-VIO/src/backend/VioBackend.cpp:3934); stereo landmarks use `SmartStereoFactor` around [VioBackend.cpp:3422](/home/yeranis/repos/V4RL/cbs_gtsam4.3/src/Kimera-VIO/src/backend/VioBackend.cpp:3422); initial priors and fixed-lag marginal `LinearContainerFactor` can also affect the state. The saved profile has `addBetweenStereoFactors:0`, lag `nr_states:25`, and `numOptimize:1`. Incoming CBS factors were absent by run metadata. **Those code paths do not reveal which factors were actually connected to the selected endpoints at updates 1084 or 1093.** The timing logger [VioBackend.cpp:4575](/home/yeranis/repos/V4RL/cbs_gtsam4.3/src/Kimera-VIO/src/backend/VioBackend.cpp:4575) reports healthy smoother status for both updates and smoother-update times `15.6792` and `17.251 ms`, with essentially zero extra-iteration time; it is not a convergence certificate.

There is one nearby frontend warning, `No corners extracted for frame with id: 2169` at log time `11:18:32.275`, before update 1084 (`11:18:34`). [The warning site](/home/yeranis/repos/V4RL/cbs_gtsam4.3/src/Kimera-VIO/src/frontend/feature-detector/FeatureDetector.cpp:160) concerns *newly extracted* corners. It does **not** establish loss of already tracked features, an outlier burst, a changed factor on 1079/1080, or any causal link. There is no retained per-update track distribution, stereo depth/parallax, reprojection residual, connected visual factor inventory, inlier count, bias/velocity state, bias covariance, or exact PIM residual to test such a link. The raw CPT7 bag alone cannot reconstruct the internal preintegrated factor and bias linearization at these late updates.

The exact surviving marginal `LinearContainerFactor`, its original linearization anchor, and pre-/post-update graph values were not saved. Consequently the requested **same post-update graph** cost test (raw/whitened, by visual/IMU/bias/prior family), `H^{-1}(-g_f)` pull analysis, marginal-prior contribution, and reference converged solve are not reproducible. Comparing costs across two different graph structures or rebuilding an approximate prior from pose logs would answer a different question. The earlier [30 s no-marginalization test](/home/yeranis/repos/gnssFGO/GLIM_KIMERA_FIXED_LAG_SEMANTICS_DEBUG.md) rules out marginalization as the *general origin* of the state/increment split, but does not exonerate or implicate its late prior at update 1084/1093. A ≤30 s cold start at physical time 215 s cannot reproduce the 25-state window, bias history, accumulated tracks, or the original marginal prior. No usable late checkpoint was found, so no additional diagnostic run was justified.

## GLIM mechanism comparison, not an ATE comparison

The already-recorded high-change section in the [previous audit](/home/yeranis/repos/gnssFGO/GLIM_KIMERA_FIXED_LAG_SEMANTICS_DEBUG.md:143) uses each source's own unchanged physical edges, not cross-source matched endpoints. Kimera's 100 local edges worsen in relative translation RMS `.035549→.059322 m` (revision zero to last); GLIM's 200 edges improve `.011716→.007953 m`. Kimera publishes an increment-composed native output while its revised CBS beliefs come from *current* smoother poses; GLIM publishes its optimized pose product and likewise needs revisions to represent its latest smoother. GLIM's corresponding active-window motion and relative changes are smaller in the recorded section (raw pose movement RMS `.000929 m`, relative-belief revision RMS `.006784 m`), versus Kimera `.224527 m` and `.044998 m` respectively. This structurally explains why source trajectories and revised-belief streams can behave differently; it does **not** isolate the late Kimera factor responsible. GLIM's exact per-update connected factor pulls were not compared because no matched Kimera graph snapshot exists.

## Validation and explicit answers

The audit processed only existing logs and IE-TC reference; no GLIM/Kimera run, fusion, CBS-ON run, graph topology experiment, or estimator change occurred. The selected analysis completed and the plot was visually checked. No production test suite or estimator build was run because no production code changed.

1. **Are revised CBS means correctly extracted?** **Yes for all 175 checked revisions.** They match the exact logged current smoother endpoint poses to `1.48e-13 m / 9.24e-15 rad`, with matching IDs/timestamps and no stale/nearest lookup. Exported full covariance matches the source log and is generated via the same-snapshot joint-marginal code path; its Hessian-level numerical correctness could not be independently retested without the graph.
2. **What source-side information causes the late translation revisions?** The directly observed cause of the *belief change* is a change in Kimera's current optimized endpoint poses, concentrated at backend updates 1084 and 1093 and shared across nearby edges. **Which visual, IMU/bias, marginal-prior, or lifecycle information drove those pose changes remains unknown** because the actual connected factors and priors were not retained. The frontend warning is only a lead, not evidence of causation.
3. **Implementation/optimizer error, or correct minimization away from IE-TC?** Neither can be decided at factor/optimizer level from these artifacts. The belief-export mean is not corrupt; smoother health/timing and covariance growth do not prove objective minimization, and no same-graph cost, factor gradient, or reference solve is possible. Do not label this simply noisy/legitimate or a marginalization bug.
4. **Change CBS revised-belief semantics?** **No evidence supports changing them.** Later revisions are genuine current-smoother relative beliefs, even when their IE-TC local error grows. This audit does not license selecting first publications by ATE or altering sender/receiver policy.
